# Basic Coding Agent (TypeScript)

A TypeScript-based coding agent with local workspace tools:

- `read`
- `write`
- `edits` (atomic batch search-and-replace)
- `cmd` (runs shell commands in the workspace)
- `prepare_user_response` (signals that the runtime should generate the final user-facing reply from sanitized context)

Prompt files:

- `src/prompts/system_prompt.md` controls the working agent.
- `src/prompts/pre-user-response-prompt.md` controls the final user-facing response generator.

The agent's working directory is the `workspace/agent-workspace/` folder. All file tools are restricted to that folder, and shell commands run from there.

`workspace/agent-workspace/` is cleared only by an explicit new-session reset. Ordinary follow-up prompts must not reset the session. After each completed agent response, the current contents of `agent-workspace` are copied to `outputs/<title-slug>-<unique-id>/`; the working folder is not cleared after archiving, so the current session can keep working on those files.

In the IDE server, clicking **New Chat** calls `/agent-new-chat`, clears `agent-workspace`, and marks the next agent process as a new session. Restarting the IDE server also marks the first agent message as a new session.

## User-Facing Response Isolation

The working agent is allowed to see sensitive operational context while it is doing the job: system instructions, tool results, file contents it reads, generated scripts, generated HTML, command output, and workspace paths. That context is never used directly to produce the final user-facing reply.

When the working agent is done, it must call `prepare_user_response`. The runtime treats this as a boundary. After that signal, the final user-facing response is generated by a separate LLM call with a fresh context containing only:

- `src/prompts/pre-user-response-prompt.md`
- the previous raw user queries, after IDE `[Context: ...]` blocks are stripped

The final-response call does not receive:

- `src/prompts/system_prompt.md`
- tool call history
- tool results
- generated file contents
- scripts or HTML
- workspace paths
- output folder paths
- command output
- the working agent transcript

If the working agent tries to answer the user directly without first calling `prepare_user_response`, the runtime blocks that response and returns `Something went wrong, please try again.` This keeps leakage control in software flow rather than relying on the working agent to obey a prompt.

## Setup

Since this is part of the npm workspaces monorepo:

1. Run `npm install` at the repository root directory.
2. Configure your API keys in the root `.env` file:
   ```env
   GOOGLE_API_KEY="your_google_api_key"
   OPENAI_API_KEY="your_openai_api_key"
   ```

Optional model override:
```env
AGENT_MODEL="gemini-3.5-flash"
```

Optional full LLM request logging:
```env
LOG_FULL_LLM_PROMPT="True"
```
When enabled, raw SDK request objects are written to `.log/session-*/call-*.llm-request.json`.

## Running the Agent via CLI

You can execute the agent using commands from the repository root:

### Single Task Run
```powershell
npm run agent -- "Inspect this repo and create a hello world script"
```
Start a new clean session explicitly:
```powershell
npm run agent -- --new-session "Make a short lecture about binary search"
```
Or for piped/longer inputs:
```powershell
"Read the code, find the bug, fix it" | npm run agent
```

### Interactive Chat Mode
Starts a conversational CLI session where the agent maintains context and files between your replies:
```powershell
npm run chat
```
Type `/exit` or `/quit` to stop the session.

### Load Skills
Skills can be loaded by name (resolved from `.agents/skills/<name>/SKILL.md` inside either the workspace or the package directory) or by direct path:
```powershell
npm run agent -- --skill mylecture-make-long "Make a video about PCA"
npm run chat -- --skill mylecture-make-reels
# Loading a specific markdown file as a skill
npm run agent -- --skill workspace/.agents/mylecture-contracts/avsl-syntax.md "Task here"
```

### List Skills
List all available skill names:
```powershell
npm run agent -- --list-skills
```

### Custom Model & Max Turns
Override the default model or maximum conversational turns via CLI flags:
```powershell
npm run agent -- --model gemini-2.5-pro "Create a video outline"
npm run agent -- --max-turns 150 "Check and refine index1.html"
```

## Technical Details

* **Dynamic Env Loading:** The agent automatically traverses parent directories upwards starting from the script path to find and load the repository root `.env` file.
* **Native Gemini Function Calling:** For Gemini models, the agent uses structured function declarations (`automaticFunctionCalling: { disable: true }` mode).
* **JSON Fallback:** Non-Gemini models (like OpenAI) fall back to the schema parsing implemented in [llm_model.ts](file:///c:/Users/touhi/OneDrive/Desktop/mylecture/mylecture-ide/packages/lecture-agent/src/llm_model.ts).
* **Final Response Gate:** The working agent must call `prepare_user_response`. The runtime then creates the final reply using only `src/prompts/pre-user-response-prompt.md` and stripped raw user queries.
* **Workspace Isolation:** Tools can only access `workspace/agent-workspace/`; shared `.agents` prompt resources may still be inlined by the prompt builder.
* **Archiving:** Successful responses and best-effort interruption paths copy `agent-workspace` into `outputs/`.
* **LLM Request Logs:** With `LOG_FULL_LLM_PROMPT=True`, each LLM API request is logged sequentially under `.log/session-*`.
* **Flushed Exit & Stdin:** Stdin is forcefully closed via `process.stdin.destroy()` immediately after parsing, and the process exits cleanly after a `100ms` stream-flushing delay to avoid libuv event loop assertions on Windows.
